# CHANGELOG — threads-rakuten-affili

## v1.1 — 比較モード追加

「コピペ3回で比較記事が1本できる」型の記事から、この運用で実際に効く4点だけを取り込んだ。
3プロンプトのコピペ連鎖そのものは**採用していない**（既に承認1行まで自動化済みで、
人間の貼り替え作業が増えるだけのため）。

### 追加

- **比較モード**（`config/comparison_template.md`）
  親1本＋ぶら下げ3本のThreadsスレッドで3商品を比較する。勝者を1つに決めず、
  3商品それぞれに「向いている人／向いていない人」を書く。
  リンク接触点が3回になり、楽天の「クリック→24h以内にかご入れ」に対する
  クリック機会が単純に3倍になるのが収益上の狙い。
- **買い替え起点の商品選定**（`config/my_products.md`）
  楽天APIの人気商品ではなく、りんりんが実際に買い替えた商品を入力にする。
  「前に何を使っていて、なぜ変えたか」はAIが書けない＝捏造禁止ルールと両立する。
  消耗品は買い替えが起きるので、同じ投稿が半年後にもう一度効く。
- **プレースホルダ方式**（`【ここに体験：〜】` / `【要確認：〜】`）
  AIは体験と数値を書かず、穴を空ける。埋めるのは人間。
  未記入のまま投稿しようとすると `threads_post.py` が機械でブロックする。
- **EPC（1クリック単価）KPI**（`weekly_review.py --clicks/--revenue/--orders/--target`）
  楽天はかごに入った商品が紹介商品と別でも成果対象になり得るので、
  商品単価ではなく1クリックあたりの実測額を主KPIにする。目標額から必要クリック数を逆算する。

### 変更

- `rakuten_search.py --keywords`：キーワード指定で候補を引くモード（比較モードの事実確認用）
- `threads_post.py`：`reply_to_id` によるぶら下げ投稿に対応（親→ぶら下げを順に公開）
- `compliance_check.py`：親＋ぶら下げを全数検査。`#PR` は親と最終ぶら下げの両方に付与
- `approval_queue.py`：スレッド投稿の表示と「📝 記入待ち」件数の表示
- `hooks_config.md`：型7「比較・買い替え」を追加（weight 0＝日次の抽選対象外）
- `scoring_rubric.md`：比較モードの減点ルール（「向いていない人」欠落 -15 など）

### 採用しなかったもの

- 3プロンプトのコピペ連鎖 … 既に自動化済み。人間の作業を増やす方向になる
- 「月50万」「100本量産」の数値 … 根拠が示されておらず、Threadsは投稿頻度に上限がある
  （Phase1は2〜3本/日）ので本数を主軸に置く設計自体が合わない
